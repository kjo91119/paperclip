# 교차검증 운영 지시서

## 1. 목적

이 문서는 STUDIOJUN이 Paperclip 안에서 CEO, CTO, CMO, 그리고 운영자(사용자)가 함께 일할 때 결과물을 서로 교차검증하는 기준 문서다.

목표는 다음 네 가지다.

1. 계획만 그럴듯하고 실행 근거가 빈약한 산출물을 막는다.
2. 기술 완성도는 높지만 고객 가치나 메시지가 약한 결과물을 막는다.
3. 마케팅 문구는 좋지만 실제 구현 범위와 어긋나는 약속을 막는다.
4. 누가 무엇을 승인했고 무엇을 근거로 진행됐는지 추적 가능하게 만든다.

이 문서는 새로운 이슈를 만들 때, 승인 요청을 검토할 때, 문서/프로토타입을 완료 처리할 때 항상 참고한다.

## 2. 현재 운영 전제

현재 기본 조직은 아래와 같다.

- CEO: 방향 수립, 우선순위, 위임, 승인 요청 생성
- CTO: 기술 브리프, 구현 범위, 품질 기준, 납품 체크리스트
- CMO: 제안 문구, 고객 적합성, 오퍼 구조, 외부 메시지
- 운영자(사용자): 최종 승인, 예산/조직 판단, 산출물 수용 여부 결정

현재 회사는 `STUDIOJUN`이며, 첫 운영 단위는 다음 흐름을 기본으로 삼는다.

1. CEO가 계획을 세운다.
2. CTO가 기술 실행 가능성과 산출물 구조를 고정한다.
3. CMO가 고객 가치와 대외 메시지를 정리한다.
4. 운영자가 최종 수용/보류/수정 요청을 결정한다.

## 3. 핵심 원칙

1. 작성자 본인이 자기 결과물을 최종 승인하지 않는다.
2. 모든 `done` 상태에는 최소 1개의 근거가 있어야 한다.
3. 근거는 말이 아니라 문서, 체크리스트, 코멘트, 산출물 링크여야 한다.
4. 계획 문서와 실제 실행 이슈가 어긋나면 실행 이슈를 멈추고 계획을 갱신한다.
5. 마케팅 메시지는 구현된 범위보다 앞서 나가면 안 된다.
6. 기술 브리프는 고객 가치와 연결되지 않으면 완료로 보지 않는다.
7. 완료 처리 전에 “무엇을 만들었는가” 뿐 아니라 “왜 이게 맞는가”를 확인한다.
8. 애매하면 진행보다 보류가 낫다. 보류 사유는 짧고 명확하게 코멘트로 남긴다.

## 4. 역할별 검증 책임

### CEO 검증 책임

CEO는 아래를 확인한다.

- 회사 목표와 현재 작업이 연결되는가
- 지금 이 작업이 가장 높은 우선순위인가
- 일이 충분히 작고 위임 가능하게 쪼개졌는가
- 다른 역할에게 넘겨야 할 작업을 본인이 붙잡고 있지 않은가
- 새 채용/새 프로젝트/새 범위 확장이 정말 필요한가

CEO는 아래 항목이 없으면 계획을 승인하지 않는다.

- 우선순위 근거
- 범위 제한 문장
- 다음 액션 3개 이내
- 어떤 역할이 이어받아야 하는지 명시

### CTO 검증 책임

CTO는 아래를 확인한다.

- 브리프가 실제 구현 가능한 범위인가
- 데모 시나리오가 너무 넓지 않은가
- 구현 완료 기준이 명확한가
- 반응형, 성능, 접근성, 가독성 기본선이 있는가
- 체크리스트가 실제 납품/리뷰에 바로 쓸 수 있는가

CTO는 아래 항목이 없으면 기술 산출물을 승인하지 않는다.

- 문제 정의
- 제약 조건
- 제외 범위
- 성공 지표
- 검토 절차

### CMO 검증 책임

CMO는 아래를 확인한다.

- 이 작업이 누구를 위한 것인지 한 문장으로 말할 수 있는가
- 첫 제안 문구가 너무 넓거나 모호하지 않은가
- 고객에게 약속하는 가치가 실제 산출물과 맞는가
- 데모 설명, 제안 메모, CTA가 일관적인가
- 구현되지 않은 기능을 암시하거나 과장하지 않는가

CMO는 아래 항목이 없으면 메시지 문서를 승인하지 않는다.

- 목표 고객
- 문제 상황
- 제공 가치
- 수용/비수용 범위
- 성공 기준

### 운영자(사용자) 검증 책임

운영자는 아래를 확인한다.

- 지금 조직 구성이 적절한가
- 새 채용이 실제 병목을 줄이는가
- 결과물이 지금 당장 필요한 목표에 맞는가
- 승인 이후 관리 비용이 과도하지 않은가
- 오늘 시점에서 이 작업을 계속 밀어도 좋은가

운영자는 아래 질문에 답이 안 나오면 승인하지 않는다.

- 왜 지금 이 작업을 해야 하는가
- 누가 이어서 책임질 것인가
- 실패하면 무엇을 되돌리면 되는가
- 산출물의 품질을 어떻게 확인할 것인가

## 5. 산출물별 교차검증 기준

### A. 계획 문서 (`plan`)

필수 확인 항목:

- 미션 요약이 3문장 이내로 설명 가능한가
- 우선순위 3개가 서로 다른 역할/단계로 분리되는가
- 첫 채용 추천에 이유와 시점이 함께 적혀 있는가
- 다음 액션이 추상적인 비전이 아니라 실행 가능한가

반려 기준:

- “좋아 보이는 아이디어”만 있고 우선순위 근거가 없음
- 조직 확장 이야기는 많은데 현재 실행 기준이 없음
- 다음 작업이 역할/담당 없이 떠 있음

### B. 브리프 문서 (`brief`)

필수 확인 항목:

- 콘셉트가 한 줄로 요약 가능함
- 문제 정의가 있음
- 사용자/사용 맥락이 있음
- 산출물 범위와 제외 범위가 동시에 적혀 있음
- 데모 시나리오가 있음
- 성공 지표가 있음

반려 기준:

- 멋있다는 표현만 있고 실제 사용 장면이 없음
- 구현 범위보다 비전 설명이 과도함
- 제외 범위가 없어서 이후 확장 해석이 가능함

### C. 체크리스트 문서 (`checklist` 또는 작업 파일)

필수 확인 항목:

- 인테이크
- 스코핑
- 구현
- 리뷰
- 핸드오프

반려 기준:

- 단계는 있는데 산출물 기준이 없음
- 누가 확인하는지 없음
- 체크했을 때 실제 완료 여부를 판단할 수 없음

### D. 제안 메모 / 오퍼 메모

필수 확인 항목:

- 목표 고객
- 수용 가능한 요청 유형
- 받지 않을 요청 유형
- 예상 리드타임
- 성공 기준
- 제안 톤

반려 기준:

- 누구에게 팔겠다는 말이 너무 넓음
- STUDIOJUN의 강점이 속도/프로토타입/인터랙션 중 무엇인지 흐림
- 아직 구현하지 않은 기능을 약속함

### E. 실제 프로토타입 / 납품 결과물

필수 확인 항목:

- 브리프와 실제 결과가 일치함
- 모바일/데스크톱 모두 기본 동작 확인
- 핵심 인터랙션이 버벅이지 않음
- CTA/카피/섹션 흐름이 일관됨
- README 또는 실행 방법이 남아 있음

반려 기준:

- 예쁘지만 핵심 메시지가 흐림
- 메시지는 좋은데 인터랙션/완성도가 약함
- 데스크톱만 되고 모바일이 무너짐
- 로컬에서 재현 실행이 안 됨

## 6. 교차검증 절차

### 단계 1. 작성자 제출

작성자는 아래 네 가지를 남긴다.

- 무엇을 만들었는지
- 어디에 저장했는지
- 어떤 기준으로 완료라고 판단했는지
- 다음으로 누구 검토가 필요한지

### 단계 2. 역할 간 1차 교차검증

- CEO 산출물은 CTO 또는 CMO가 검토한다.
- CTO 산출물은 CEO 또는 운영자가 검토한다.
- CMO 산출물은 CEO 또는 운영자가 검토한다.
- 최종 납품물은 가능하면 CTO와 CMO가 각각 다른 관점에서 모두 본다.

### 단계 3. 불일치 기록

불일치가 있으면 아래 형식으로 코멘트를 남긴다.

- 관찰: 무엇이 어긋났는가
- 영향: 왜 문제인가
- 요청: 무엇을 수정해야 하는가
- 기준: 어떤 문서/목표와 충돌하는가

예시:

- 관찰: 제안 메모는 2일 내 납품을 약속하지만 브리프는 5개 섹션과 복잡한 인터랙션을 요구합니다.
- 영향: 일정과 약속이 어긋나 고객 기대를 잘못 만들 수 있습니다.
- 요청: 범위를 줄이거나 리드타임을 조정하세요.
- 기준: STU-2 제안 메모, STU-3 브리프.

### 단계 4. 수정 후 재검토

수정자는 아래를 남긴다.

- 무엇을 바꿨는지
- 어떤 피드백을 반영했는지
- 아직 남은 리스크가 있는지

### 단계 5. 운영자 최종 판단

운영자는 아래 셋 중 하나만 선택한다.

- 승인: 현재 수준으로 다음 단계 진행
- 보류: 리스크 해소 전까지 멈춤
- 수정 요청: 구체적 수정사항과 함께 재작업

## 7. 완료 처리 최소 증거 규칙

모든 `done` 이슈는 최소 아래 중 하나 이상을 반드시 가져야 한다.

- 문서 1개 이상
- 코멘트 1개 이상
- 작업 산출물 링크 1개 이상
- 체크리스트/파일 경로 1개 이상

권장 규칙:

- 전략/계획 이슈: 문서 + 코멘트
- 기술 브리프: 문서 + 코멘트
- 체크리스트: 문서 또는 파일 경로 + 코멘트
- 구현 작업: 산출물 링크 + 실행 방법 + 코멘트

## 8. 승인 요청 검토 규칙

### 채용 승인

반드시 확인할 것:

- 왜 기존 인력으로 안 되는가
- 어떤 이슈가 막혀 있는가
- 새 역할이 맡을 책임이 한 문장으로 설명되는가
- 새 역할이 또 다른 역할 채용을 연쇄적으로 부르지 않는가

### 전략 승인

반드시 확인할 것:

- 현재 목표와 직접 연결되는가
- 1주 안에 검증 가능한가
- 측정 가능한 결과가 있는가

### 예산 초과 승인

반드시 확인할 것:

- 예산 초과 이유가 일시적인가 구조적인가
- 승인 시 얻는 가치가 명확한가
- 비승인 시 대체 경로가 있는가

## 9. 운영자가 바로 붙여넣어 쓸 수 있는 검토 지시문

### CEO 검토 요청 템플릿

```text
현재 계획 문서를 교차검증하라.

반드시 확인할 것:
- 회사 목표와 직접 연결되는가
- 우선순위가 3개 이내로 명확한가
- 다음 작업이 작고 위임 가능하게 나뉘어 있는가
- 채용/조직 확장이 정말 필요한가

출력 형식:
1. 유지할 점
2. 수정할 점
3. 지금 승인 가능한지 여부
```

### CTO 검토 요청 템플릿

```text
현재 브리프 또는 구현 계획을 기술 관점에서 교차검증하라.

반드시 확인할 것:
- 구현 범위가 현실적인가
- 제외 범위가 명확한가
- 반응형/성능/가독성 기준이 있는가
- 완료 기준이 문서화되어 있는가

출력 형식:
1. 기술적으로 안전한 점
2. 범위/품질 리스크
3. 수정 후 진행 조건
```

### CMO 검토 요청 템플릿

```text
현재 제안 메모 또는 데모 메시지를 고객/포지셔닝 관점에서 교차검증하라.

반드시 확인할 것:
- 목표 고객이 명확한가
- 제공 가치가 한 문장으로 설명 가능한가
- 실제 구현 범위를 넘는 약속이 없는가
- CTA와 메시지 톤이 일관적인가

출력 형식:
1. 잘 맞는 메시지
2. 혼란을 주는 메시지
3. 수정해야 할 약속/표현
```

### 운영자 최종 판단 템플릿

```text
아래 산출물을 최종 검토한다.

확인 항목:
- 계획/브리프/메시지/결과물이 서로 충돌하지 않는가
- 지금 상태로 다음 단계 진행이 가능한가
- 리스크가 남아 있다면 어디서 멈춰야 하는가

반드시 아래 형식으로 답하라.
- 결정: 승인 / 보류 / 수정 요청
- 근거: 3줄 이내
- 다음 행동: 3개 이내
```

## 10. 일상 운영 루프

권장 운영 루프는 아래와 같다.

1. CEO가 하루 시작 시 우선순위 재확인
2. CTO가 기술 산출물과 체크리스트 갱신
3. CMO가 외부 메시지/제안 문구 점검
4. 운영자가 승인 대기함과 주요 이슈 상태 확인
5. 완료 이슈는 증거가 있는지 보고 `done` 유지 여부 판단

## 11. 중단 조건

아래 상황이면 즉시 진행을 멈추고 수정 요청 또는 보류로 전환한다.

- 브리프와 결과물이 다름
- 마케팅 메시지가 실제 구현 범위를 넘음
- 승인 없이 새 에이전트/새 예산/새 범위가 확장됨
- 완료 처리됐지만 문서/코멘트/산출물 근거가 없음
- 핵심 기능이 로컬에서 재현되지 않음

## 12. 백업 및 복구 규칙

항상 두 종류를 분리해서 본다.

1. 코드 백업
2. 인스턴스 데이터 백업

현재 최신 경로와 포크 정보는 아래 파일에서 확인한다.

- `.local/LOCAL_PROJECT_MEMORY.md`

복구 전 확인할 것:

- 복구 대상이 코드인지, Paperclip 회사 데이터인지
- 현재 실행 중인 인스턴스를 덮어써도 되는지
- 백업 시각이 원하는 상태 이후인지 이전인지

## 13. 마지막 체크

운영자는 최종 승인 전에 아래 질문에 모두 `예`라고 답할 수 있어야 한다.

- 지금 이 결과물이 처음 목표와 이어지는가
- 누가 왜 승인했는지 기록이 남아 있는가
- 다음 담당자가 바로 이어받을 수 있는가
