# STUDIOJUN 로컬 교차검증 운영 지시서

## 1. 범위

이 문서는 현재 로컬에서 운영 중인 `STUDIOJUN` 회사를 위한 운영 플레이북이다.

중요:

- 공식 Paperclip 제품 정의는 [PRODUCT.md](./PRODUCT.md)를 따른다.
- 이 문서는 Paperclip 제품 전체의 일반 정책이 아니라, 그 위에서 STUDIOJUN을 운영하기 위해 덧씌운 로컬 운영 템플릿이다.
- 따라서 여기의 오퍼 메모, 브리프, 프로토타입, 모바일/데스크톱 검수 규칙은 STUDIOJUN의 현재 업무 성격을 반영한 것이다.

즉, 이 문서는 다음 성격을 가진다.

- 저장소 전체의 일반 정책 문서가 아니다.
- 현재 STUDIOJUN 회사와 그 하위 이슈를 교차검증할 때 쓰는 실무 문서다.
- 다른 회사나 다른 운영 방식에 그대로 복사하기보다, 상태 매핑과 역할을 먼저 점검한 뒤 조정해서 써야 한다.

이 문서의 목적은 네 가지다.

1. 계획만 그럴듯하고 실행 근거가 빈약한 산출물을 막는다.
2. 기술 완성도는 높지만 고객 가치나 메시지가 약한 결과물을 막는다.
3. 마케팅 문구는 좋지만 실제 구현 범위와 어긋나는 약속을 막는다.
4. 누가 무엇을 근거로 진행했고, 그 판단이 Paperclip 안에서 어떤 상태로 남는지 추적 가능하게 만든다.

## 2. 용어 정의

이 문서에서는 아래 용어를 엄격히 구분한다.

### 리뷰

- CEO, CTO, CMO, 운영자가 문서나 결과물을 읽고 의견을 남기는 행위
- 보통 코멘트, 이슈 문서 수정 요청, 체크리스트 확인으로 남긴다
- 리뷰 자체는 Paperclip의 `approval` 상태를 바꾸지 않는다

### 수용 추천

- 특정 역할이 “이 결과물은 자기 기능 관점에서 다음 단계로 넘어갈 수 있다”고 판단하는 것
- 예: CTO가 브리프를 기술적으로 수용 가능하다고 판단
- 이것도 리뷰의 일종이며, 시스템 승인과 다르다

### 시스템 승인

- Paperclip의 `approval` 객체에 대해 실제 상태 전이를 일으키는 행위
- 데이터 모델에는 `pending`, `revision_requested`, `approved`, `rejected`, `cancelled`가 있다
- 하지만 현재 보드 UI/API에서 운영자가 실제로 쓰는 경로는 `approve`, `reject`, `request-revision`, `resubmit`이다
- 따라서 이 지시서의 운영 규칙에서는 `cancelled`를 일반 승인 결정 경로로 쓰지 않는다
- 실제 제품 동작상 `approve`, `reject`, `request-revision`은 보드/운영자만 수행할 수 있다

### 운영자 최종 판단

- 운영자(사용자)가 리뷰 결과를 보고 “승인 / 보류 / 수정 요청” 중 하나를 결정하는 것
- 이 판단은 반드시 Issue 상태, Approval 상태, 코멘트 중 최소 하나로 제품 안에 기록되어야 한다
- 말로만 합의하고 상태를 남기지 않는 것은 금지한다

## 3. Paperclip 안에서 실제로 남겨야 하는 기록

교차검증 결과는 반드시 Paperclip 안의 아래 객체로 남긴다.

1. 이슈 상태
2. 승인 객체 상태
3. 이슈 문서
4. 이슈 코멘트
5. 승인 코멘트 (`approval_comments`)
6. 첨부나 워크프로덕트 링크

권장 원칙:

- 감사 근거의 1차 저장소는 Paperclip 안이어야 한다.
- 로컬 파일 경로, 워크스페이스 파일, `.local/LOCAL_PROJECT_MEMORY.md` 같은 저장소 밖/회사 밖 정보는 보조 메모로만 취급한다.
- 로컬 파일을 썼다면, 그 핵심 요약과 판단 근거를 반드시 해당 이슈 코멘트나 문서에도 남긴다.

금지 원칙:

- “파일은 로컬에 있으니 됐다”를 완료 근거로 삼지 않는다.
- 승인 판단을 채팅이나 구두 합의로만 남기지 않는다.

## 4. 실제 상태값과 운영 의미

### 이슈 상태

현재 사용 가능한 주요 이슈 상태는 아래와 같다.

- `backlog`
- `todo`
- `in_progress`
- `in_review`
- `done`
- `blocked`
- `cancelled`

권장 의미:

- `backlog`: 아직 착수하지 않은 후보 작업
- `todo`: 범위는 정해졌고 바로 시작 가능한 작업
- `in_progress`: 현재 누군가가 실행 중인 작업
- `in_review`: 실행은 끝났고 검토/교차검증 중인 작업
- `blocked`: 외부 결정, 승인, 자원, 정보 부족으로 진행 불가한 작업
- `done`: 결과와 근거가 확인되어 종료 가능한 작업
- `cancelled`: 더 이상 진행하지 않기로 명시한 작업

### 승인 상태

현재 사용 가능한 승인 상태는 아래와 같다.

- `pending`
- `revision_requested`
- `approved`
- `rejected`
- `cancelled`

중요:

- 이 상태는 `approval` 객체에만 적용된다.
- 리뷰어의 코멘트가 자동으로 승인 상태가 되지 않는다.
- `approve`, `reject`, `request-revision`은 운영자/보드가 수행한다.
- `cancelled`는 현재 상수에는 있지만, 일반 보드 UI/API의 표준 운영 경로로 노출되어 있지 않다.
- 따라서 일반 운영에서는 `approved`, `rejected`, `revision_requested`, `pending` 중심으로 기록한다.

## 5. 운영자 판단과 실제 상태 매핑

교차검증 후 운영자는 아래 매핑을 기본 규칙으로 사용한다.

중요 구현 주의:

- 아래 규칙은 현재 STUDIOJUN 운영 정책이다.
- 현재 Paperclip 서버는 상태값 유효성, 일부 전이 부수효과, 일부 불변식만 강제한다.
- `in_review`, `blocked`, `done`의 운영 의미와 `done` 이전 최소 증거 존재 여부는 아직 서버가 전부 자동 강제하지 않으므로 운영자가 직접 확인하고 기록해야 한다.

### 결정: 승인

조건:

- 결과물이 현재 목표에 맞고
- 리스크가 허용 가능하며
- 다음 단계로 넘어가도 되는 경우

기록 방식:

- 승인 객체가 있는 경우: `approval.status = approved`
- 승인과 연결된 이슈는 자동으로 `done`으로 닫지 않는다
- 승인 후 실제 후속 조치가 남아 있으면 연결 이슈는 `in_progress` 또는 `in_review`로 유지한다
- 연결 이슈를 `done`으로 바꾸는 시점은 요청한 에이전트가 승인 결과를 반영하고, 종료 근거를 남기고, 닫을 준비가 되었을 때다
- 승인 객체가 없고 후속 조치도 남아 있지 않은 검토 중 이슈만 `issue.status = done` 후보가 된다
- 다음 후속 작업이 있다면: 후속 이슈를 `todo` 또는 `in_progress`로 열기
- 운영자 코멘트에 승인 근거 3줄 이내로 남기기

### 결정: 보류

조건:

- 지금은 진행하면 안 되지만
- 작업 자체를 폐기할 정도는 아닌 경우
- 외부 입력, 추가 자료, 권한, 인력, 승인 대기 등이 필요한 경우

기록 방식:

- 이슈는 원칙적으로 `blocked`
- 보류 사유를 코멘트로 남기기
- 별도 승인 객체가 있다면 상태는 즉시 바꾸지 말고, 실제 승인 검토가 멈춘 경우에만 운영자가 `revision_requested` 또는 `rejected`를 선택한다

주의:

- “검토 중이라 멈춤”은 `blocked`가 아니라 `in_review`가 더 맞다
- `blocked`는 진행 불능 원인이 명확할 때만 쓴다

### 결정: 수정 요청

조건:

- 방향은 유지하지만 재작업이 필요한 경우
- 다시 고쳐와서 재검토할 가치가 있는 경우

기록 방식:

- 승인 객체가 있는 경우: `approval.status = revision_requested`
- 승인 객체가 없는 문서/산출물 검토인 경우:
  - 재작업이 즉시 가능한 경우 `issue.status = in_review` 유지 또는 `in_progress`로 복귀
  - 외부 입력 없이는 못 고치는 경우 `issue.status = blocked`
- 운영자 코멘트에 수정 항목을 관찰 / 영향 / 요청 / 기준 형식으로 남기기

### 결정: 거절 또는 취소

조건:

- 이 방향으로 더 진행하지 않기로 했거나
- 승인 요청 자체를 폐기하는 편이 맞는 경우

기록 방식:

- 승인 객체가 있으면 `rejected`
- 더 이상 작업하지 않을 이슈면 `cancelled`
- 현재 일반 운영 절차에서는 승인 객체에 `cancelled`를 쓰지 않는다
- 왜 거절했는지와 대체 방향이 있는지 코멘트 남기기

## 6. 문서 키 규칙

중요:

- Paperclip에서 문서 키는 현재 구현상 자유 문자열이 아니다.
- 소문자 영문/숫자와 `_`, `-`만 허용되고, 길이 제한도 있다.
- 라우트는 문서 키를 소문자로 정규화해 처리한다.
- 시스템적으로 특별 취급되는 문서는 사실상 `plan`이 핵심이다.
- `brief`, `checklist`, `memo`는 제품의 고정 문서 타입이 아니라 STUDIOJUN 운영 컨벤션이다.

따라서 이 문서에서 아래 표현은 모두 “운영 관례”로 이해한다.

- `plan`
- `brief`
- `checklist`
- `memo`

권장 규칙:

- 계획 문서: `plan`
- 브리프 문서: `brief` 또는 `brief_v1`
- 제안 메모: `memo`
- 체크리스트: `checklist` 또는 `launch-plan` 같은 명확한 slug 키

## 7. 승인 요청 생성 규칙

승인 요청을 만들 때는 아래를 운영 기본 규칙으로 둔다.

구현 주의:

- 현재 제품 API는 `issueIds` 없이 승인 요청을 생성할 수 있다.
- 승인 코멘트도 승인 생성과 별도 호출이다.
- 따라서 아래 항목은 서버가 전부 자동 강제하는 계약이 아니라, 운영자가 생성 직후 연결과 코멘트를 보강해야 하는 규칙이다.

1. 승인 요청은 가능한 한 원본 이슈와 연결한다.
2. `issueIds`를 비워서 만들지 않는다, 특별한 이유가 없는 한 최소 1개 이상 연결한다.
3. 승인 요청 코멘트에는 “왜 이 승인이 필요한가”를 남긴다.
4. 승인 후 어떤 에이전트를 깨울지, 어떤 이슈를 다시 열지 명시한다.

예:

- 채용 승인: 막힌 원본 이슈를 `issueIds`로 연결
- 전략 승인: 해당 전략이 파생된 계획 이슈를 `issueIds`로 연결
- 예산 승인: 비용 초과가 발생한 실행 이슈 또는 프로젝트 이슈를 연결

## 8. 현재 역할 구조

현재 기본 조직은 아래와 같다.

- CEO: 방향 수립, 우선순위, 위임, 승인 요청 생성
- CTO: 기술 브리프, 구현 범위, 품질 기준, 납품 체크리스트
- CMO: 제안 문구, 고객 적합성, 오퍼 구조, 외부 메시지
- 운영자(사용자): 최종 승인, 예산/조직 판단, 상태 기록, 수용 여부 결정

현재 회사는 `STUDIOJUN`이며, 첫 운영 단위는 다음 흐름을 기본으로 삼는다.

1. CEO가 계획을 세운다.
2. CTO가 기술 실행 가능성과 산출물 구조를 검토한다.
3. CMO가 고객 가치와 대외 메시지를 검토한다.
4. 운영자가 실제 상태 전이와 최종 판단을 기록한다.

주의:

- 이 흐름은 STUDIOJUN의 현재 1차 운영 루프다.
- 다른 회사에서는 CMO가 없거나, 오퍼 메모 대신 연구 브리프가 중심일 수 있다.
- 그 경우 역할은 유지하되 산출물 기준은 회사 성격에 맞게 바꿔야 한다.

## 9. 핵심 원칙

1. 작성자 본인이 자기 결과물을 최종 수용하지 않는다.
2. 리뷰 코멘트와 시스템 승인 상태를 혼동하지 않는다.
3. 모든 `done` 이슈에는 최소 1개의 제품 안 근거가 있어야 한다.
4. 근거는 가능하면 이슈 문서, 이슈 코멘트, 첨부, 워크프로덕트로 남긴다.
5. 계획 문서와 실제 실행 이슈가 어긋나면 실행 이슈를 멈추고 계획을 갱신한다.
6. 마케팅 메시지는 구현된 범위보다 앞서 나가면 안 된다.
7. 기술 브리프는 고객 가치와 연결되지 않으면 완료로 보지 않는다.
8. 애매하면 `done`보다 `in_review` 또는 `blocked`가 낫다.

## 10. 역할별 검증 책임

### CEO 검증 책임

CEO는 아래를 확인한다.

- 회사 목표와 현재 작업이 연결되는가
- 지금 이 작업이 가장 높은 우선순위인가
- 일이 충분히 작고 위임 가능하게 쪼개졌는가
- 다른 역할에게 넘겨야 할 작업을 본인이 붙잡고 있지 않은가
- 새 채용/새 프로젝트/새 범위 확장이 정말 필요한가

CEO는 아래 항목이 없으면 “수용 추천”을 하지 않는다.

- 우선순위 근거
- 범위 제한 문장
- 다음 액션 3개 이내
- 어떤 역할이 이어받아야 하는지 명시

### CTO 검증 책임

CTO는 아래를 확인한다.

- 브리프가 실제 구현 가능한 범위인가
- 데모 시나리오가 너무 넓지 않은가
- 구현 완료 기준이 명확한가
- 반응형, 성능, 접근성, 가독성 기본선이 있는가
- 체크리스트가 실제 납품/리뷰에 바로 쓸 수 있는가

CTO는 아래 항목이 없으면 “기술적 수용 추천”을 하지 않는다.

- 문제 정의
- 제약 조건
- 제외 범위
- 성공 지표
- 검토 절차

### CMO 검증 책임

CMO는 아래를 확인한다.

- 이 작업이 누구를 위한 것인지 한 문장으로 말할 수 있는가
- 첫 제안 문구가 너무 넓거나 모호하지 않은가
- 고객에게 약속하는 가치가 실제 산출물과 맞는가
- 데모 설명, 제안 메모, CTA가 일관적인가
- 구현되지 않은 기능을 암시하거나 과장하지 않는가

CMO는 아래 항목이 없으면 “메시지 수용 추천”을 하지 않는다.

- 목표 고객
- 문제 상황
- 제공 가치
- 수용/비수용 범위
- 성공 기준

### 운영자(사용자) 검증 책임

운영자는 아래를 확인한다.

- 지금 조직 구성이 적절한가
- 새 채용이 실제 병목을 줄이는가
- 결과물이 지금 당장 필요한 목표에 맞는가
- 승인 이후 관리 비용이 과도하지 않은가
- 오늘 시점에서 이 작업을 계속 밀어도 좋은가

운영자는 아래 질문에 답이 안 나오면 상태를 확정하지 않는다.

- 왜 지금 이 작업을 해야 하는가
- 누가 이어서 책임질 것인가
- 실패하면 무엇을 되돌리면 되는가
- 산출물의 품질을 어떻게 확인할 것인가

### 운영자가 작성자인 경우 예외 규칙

현재 V1 운영에서는 최종 상태 전이를 실제로 남길 수 있는 인간 운영자가 한 명뿐인 경우가 많다.

따라서 운영자 본인이 문서나 결과물을 직접 작성했을 때는 아래 예외 규칙을 쓴다.

기본 규칙:

1. 운영자 작성 결과물은 바로 `done` 또는 `approved`로 넘기지 않는다.
2. 먼저 해당 이슈를 `in_review`로 둔다.
3. 관련 역할의 에이전트에게 최소 1회의 리뷰 코멘트를 받는다.
4. 그 리뷰를 바탕으로 운영자가 최종 상태를 기록한다.

권장 리뷰 담당:

- 전략/우선순위 문서: CEO
- 기술 브리프/프로토타입: CTO
- 제안 메모/카피/포지셔닝: CMO

운영자 단독 최종 판단이 허용되는 예외:

- 긴급 복구
- 보안상 즉시 중단이 필요한 경우
- 개발 환경 장애 대응

이 예외를 쓸 때는 반드시 남긴다.

- 왜 즉시 처리했는지
- 왜 사전 리뷰를 생략했는지
- 사후 리뷰가 필요한지

사후 리뷰가 필요하면 같은 날 후속 이슈 또는 코멘트로 남긴다.

## 11. 산출물별 교차검증 기준

### A. 계획 문서 (`plan`)

필수 확인 항목:

- 미션 요약이 3문장 이내로 설명 가능한가
- 우선순위 3개가 서로 다른 역할/단계로 분리되는가
- 채용이 필요한 계획이라면 첫 채용 추천에 이유와 시점이 함께 적혀 있는가
- 다음 액션이 추상적인 비전이 아니라 실행 가능한가

반려 기준:

- 좋아 보이는 아이디어만 있고 우선순위 근거가 없음
- 조직 확장 이야기는 많은데 현재 실행 기준이 없음
- 다음 작업이 역할/담당 없이 떠 있음

### B. 브리프 문서 (`brief`, 운영 관례)

필수 확인 항목:

- 콘셉트가 한 줄로 요약 가능함
- 문제 정의가 있음
- 사용자/사용 맥락이 있음
- 산출물 범위와 제외 범위가 동시에 적혀 있음
- 데모 시나리오가 있음
- 성공 지표가 있음

반려 기준:

- 멋있다는 표현만 있고 실제 사용 장면이 없음
- 구현 범위보다 비전 설명이 과도함
- 제외 범위가 없어서 이후 확장 해석이 가능함

### C. 체크리스트 문서 (`checklist`, 운영 관례) 또는 작업 파일

필수 확인 항목:

- 작업 성격에 맞는 단계 구분이 있는가
- 필요한 경우 인테이크 / 스코핑 / 구현 / 리뷰 / 핸드오프 중 relevant 단계가 포함되는가
- 아주 작은 유지보수 작업이라면 왜 일부 단계가 생략되는지 설명이 있는가

반려 기준:

- 단계는 있는데 산출물 기준이 없음
- 누가 확인하는지 없음
- 체크했을 때 실제 완료 여부를 판단할 수 없음

### D. 제안 메모 / 오퍼 메모 (`memo`, 운영 관례)

필수 확인 항목:

- 목표 고객
- 수용 가능한 요청 유형
- 받지 않을 요청 유형
- 예상 리드타임
- 성공 기준
- 제안 톤

반려 기준:

- 누구에게 팔겠다는 말이 너무 넓음
- STUDIOJUN의 강점이 속도, 프로토타입, 인터랙션 중 무엇인지 흐림
- 아직 구현하지 않은 기능을 약속함

### E. 실제 프로토타입 / 납품 결과물

주의:

- 이 섹션은 STUDIOJUN의 현재 작업이 웹 프로토타입 중심이기 때문에 포함되어 있다.
- 다른 회사가 리서치, 운영 자동화, 문서 생산이 중심이면 이 기준을 그대로 쓰지 말고 해당 산출물 기준으로 바꿔야 한다.

필수 확인 항목:

- 브리프와 실제 결과가 일치함
- 모바일과 데스크톱 모두 기본 동작 확인
- 핵심 인터랙션이 버벅이지 않음
- CTA, 카피, 섹션 흐름이 일관됨
- README 또는 실행 방법이 남아 있음

이 Paperclip 저장소 자체를 수정하는 코드/실행 변경이 포함된 경우 추가 필수 확인 항목:

- `pnpm -r typecheck`
- `pnpm test:run`
- `pnpm build`

위 세 명령은 이 저장소 기준 기본 완료 검증 계약이다.

- 원칙적으로 셋 다 통과해야 `done` 후보가 된다
- 하나라도 실행하지 못했으면 무엇을 실행하지 못했는지와 이유를 코멘트에 남긴다
- 미실행 항목이 남아 있으면 기본 상태는 `in_review`이며, 운영자가 예외를 명시적으로 수용할 때만 종료 가능하다
- 외부 repo 또는 별도 워크스페이스 산출물을 검토하는 경우에는 그 대상 저장소의 검증 계약을 우선 적용한다

반려 기준:

- 예쁘지만 핵심 메시지가 흐림
- 메시지는 좋은데 인터랙션/완성도가 약함
- 데스크톱만 되고 모바일이 무너짐
- 로컬에서 재현 실행이 안 됨
- 코드 변경이 있는데 검증 명령 결과가 없거나 누락 사유가 없음

## 12. 교차검증 절차

### 단계 1. 작성자 제출

작성자는 아래 네 가지를 남긴다.

- 무엇을 만들었는지
- 어디에 저장했는지
- 어떤 기준으로 완료라고 판단했는지
- 다음으로 누구 검토가 필요한지

권장:

- 가능하면 이슈 문서 또는 코멘트로 남긴다
- 로컬 워크스페이스 파일만 남기지 않는다

### 단계 2. 역할 간 1차 리뷰

- CEO 산출물은 CTO 또는 CMO가 리뷰한다.
- CTO 산출물은 CEO 또는 운영자가 리뷰한다.
- CMO 산출물은 CEO 또는 운영자가 리뷰한다.
- 최종 납품물은 가능하면 CTO와 CMO가 각각 다른 관점에서 모두 본다.

중요:

- 이 단계는 “리뷰”다.
- 이 단계에서 승인 객체 상태가 바뀌는 것은 아니다.

### 단계 3. 불일치 기록

불일치가 있으면 아래 형식으로 코멘트를 남긴다.

- 관찰: 무엇이 어긋났는가
- 영향: 왜 문제인가
- 요청: 무엇을 수정해야 하는가
- 기준: 어떤 문서나 목표와 충돌하는가

예시:

- 관찰: 제안 메모는 2일 내 납품을 약속하지만 브리프는 5개 섹션과 복잡한 인터랙션을 요구합니다.
- 영향: 일정과 약속이 어긋나 고객 기대를 잘못 만들 수 있습니다.
- 요청: 범위를 줄이거나 리드타임을 조정하세요.
- 기준: STU-2 제안 메모, STU-3 브리프.

### 단계 4. 수정 후 재검토

수정자는 아래를 남긴다.

- 무엇을 바꿨는지
- 어떤 피드백을 반영했는지
- 아직 남은 리스크가 있는지

### 단계 5. 운영자 최종 판단

운영자는 아래 셋 중 하나를 선택한다.

- 승인
- 보류
- 수정 요청

그리고 반드시 대응되는 상태를 우선 기록한다.

- 이슈 판단이면 `issue.status`
- 승인 판단이면 `approval.status`

코멘트는 상태 전이를 대체하는 기본 수단이 아니라, 상태 판단의 근거와 예외를 설명하는 보강 수단으로 쓴다.

상태를 실제로 바꾸기 어려운 예외 상황에서만 코멘트만 남길 수 있다.

예:

- 시스템 장애로 상태 전이가 실패한 경우
- 후속 검토가 같은 턴 안에 이어져 아직 최종 상태를 확정하지 않는 경우

이 경우에도 운영자는 코멘트에 아래를 남긴다.

- 왜 상태를 즉시 못 바꿨는지
- 목표 상태가 무엇인지
- 누가 언제 후속 상태 전이를 마무리할지

그리고 가능한 빨리 아래 중 하나 이상을 제품 안에 기록한다.

- 이슈 상태 전이
- 승인 상태 전이
- 운영자 코멘트
- 필요하면 승인 코멘트

## 13. 완료 처리 최소 증거 규칙

운영 규칙상 모든 `done` 이슈는 최소 아래 중 하나 이상을 반드시 가져야 한다.

- 이슈 문서 1개 이상
- 이슈 코멘트 1개 이상
- 첨부 또는 워크프로덕트 링크 1개 이상

구현 주의:

- 현재 서버는 `done` 전환 전에 이 증거 존재를 자동 검사하지 않는다.
- 따라서 운영자가 상태를 `done`으로 바꾸기 전에 직접 확인하고, 부족하면 먼저 문서/코멘트/링크를 남겨야 한다.

추가 규칙:

- 승인 중심 작업이면 승인 코멘트도 강한 근거로 인정한다
- 이 Paperclip 저장소 자체를 수정하는 코드/프로토타입/실행 변경 작업은 위 증거에 더해 검증 명령 결과가 필요하다
- 이 저장소의 코드 작업 기본 검증 명령은 `pnpm -r typecheck`, `pnpm test:run`, `pnpm build`다
- 외부 repo 또는 별도 워크스페이스 작업은 그 대상 저장소의 검증 계약을 따른다
- 미실행 항목이 있으면 그 이유와 영향 범위를 이슈 또는 승인 코멘트에 남긴다
- 미실행 상태를 운영자가 명시적으로 수용하지 않았다면 `done`으로 닫지 않는다

보조 증거로만 허용되는 것:

- 워크스페이스 파일 경로
- 로컬 파일 경로
- `.local/LOCAL_PROJECT_MEMORY.md`

보조 증거를 썼다면 추가 규칙:

- 핵심 판단 내용과 요약을 이슈 문서 또는 코멘트에 다시 남긴다.

권장 규칙:

- 전략/계획 이슈: 문서 + 코멘트
- 기술 브리프: 문서 + 코멘트
- 체크리스트: 문서 + 코멘트
- 구현 작업: 산출물 링크 + 실행 방법 + 코멘트

## 14. 승인 요청 검토 규칙

### 채용 승인

반드시 확인할 것:

- 왜 기존 인력으로 안 되는가
- 어떤 이슈가 막혀 있는가
- 새 역할이 맡을 책임이 한 문장으로 설명되는가
- 새 역할이 또 다른 역할 채용을 연쇄적으로 부르지 않는가
- 원본 이슈가 `issueIds`로 연결되어 있는가

### 전략 승인

반드시 확인할 것:

- 현재 목표와 직접 연결되는가
- 1주 안에 검증 가능한가
- 측정 가능한 결과가 있는가
- 승인 요청이 원본 계획 이슈와 연결되어 있는가

### 예산 초과 승인

반드시 확인할 것:

- 예산 초과 이유가 일시적인가 구조적인가
- 승인 시 얻는 가치가 명확한가
- 비승인 시 대체 경로가 있는가
- 해당 실행 이슈나 프로젝트 이슈가 연결되어 있는가

## 15. 운영자가 바로 붙여넣어 쓸 수 있는 검토 지시문

### CEO 리뷰 요청 템플릿

```text
현재 계획 문서를 교차검증하라.

반드시 확인할 것:
- 회사 목표와 직접 연결되는가
- 우선순위가 3개 이내로 명확한가
- 다음 작업이 작고 위임 가능하게 나뉘어 있는가
- 채용/조직 확장이 정말 필요한가

출력 형식:
1. 유지할 점
2. 수정할 점
3. 지금 수용 추천 가능한지 여부
```

### CTO 리뷰 요청 템플릿

```text
현재 브리프 또는 구현 계획을 기술 관점에서 교차검증하라.

반드시 확인할 것:
- 구현 범위가 현실적인가
- 제외 범위가 명확한가
- 반응형/성능/가독성 기준이 있는가
- 완료 기준이 문서화되어 있는가

출력 형식:
1. 기술적으로 안전한 점
2. 범위/품질 리스크
3. 수정 후 진행 조건
```

### CMO 리뷰 요청 템플릿

```text
현재 제안 메모 또는 데모 메시지를 고객/포지셔닝 관점에서 교차검증하라.

반드시 확인할 것:
- 목표 고객이 명확한가
- 제공 가치가 한 문장으로 설명 가능한가
- 실제 구현 범위를 넘는 약속이 없는가
- CTA와 메시지 톤이 일관적인가

출력 형식:
1. 잘 맞는 메시지
2. 혼란을 주는 메시지
3. 수정해야 할 약속/표현
```

### 운영자 최종 판단 템플릿

```text
아래 산출물을 최종 검토한다.

확인 항목:
- 계획, 브리프, 메시지, 결과물이 서로 충돌하지 않는가
- 지금 상태로 다음 단계 진행이 가능한가
- 리스크가 남아 있다면 어디서 멈춰야 하는가
- 이 판단이 Issue 상태 또는 Approval 상태로 어떻게 기록될지 명확한가

반드시 아래 형식으로 답하라.
- 결정: 승인 / 보류 / 수정 요청
- 상태 기록: issue=<...>, approval=<없음 또는 상태값>
- 근거: 3줄 이내
- 다음 행동: 3개 이내
```

## 16. 일상 운영 루프

권장 운영 루프는 아래와 같다.

1. CEO가 하루 시작 시 우선순위 재확인
2. CTO가 기술 산출물과 체크리스트 갱신
3. CMO가 외부 메시지와 제안 문구 점검
4. 운영자가 승인 대기함과 주요 이슈 상태 확인
5. 완료 이슈는 증거가 있는지 보고 `done` 유지 여부 판단

## 17. 중단 조건

아래 상황이면 즉시 진행을 멈추고 수정 요청 또는 보류로 전환한다.

- 브리프와 결과물이 다름
- 마케팅 메시지가 실제 구현 범위를 넘음
- 승인 없이 새 에이전트, 새 예산, 새 범위가 확장됨
- 완료 처리됐지만 문서, 코멘트, 첨부, 워크프로덕트 근거가 없음
- 핵심 기능이 로컬에서 재현되지 않음

## 18. 백업 및 복구 규칙

항상 두 종류를 분리해서 본다.

1. 코드 백업
2. 인스턴스 데이터 백업

현재 최신 경로와 포크 정보는 아래 파일에서 확인한다.

- `.local/LOCAL_PROJECT_MEMORY.md`

중요:

- 이 파일은 운영자 메모다.
- 감사 근거나 완료 근거의 1차 저장소로 쓰지 않는다.

활성 인스턴스 확인 원칙:

- 아래 경로는 예시일 뿐이며, 먼저 현재 활성 인스턴스가 어디인지 확인해야 한다.
- 기본 인스턴스는 보통 `~/.paperclip/instances/default`다.
- 커스텀 환경은 `PAPERCLIP_HOME`, `PAPERCLIP_INSTANCE_ID`를 따른다.
- worktree-local 환경은 repo-local `.paperclip/.env` 또는 `~/.paperclip-worktrees/instances/<worktree-id>/`를 사용할 수 있다.
- 같은 명령이라도 어떤 인스턴스를 가리키는지부터 확인한 뒤 백업/복구한다.

복구 전 확인할 것:

- 복구 대상이 코드인지, Paperclip 회사 데이터인지
- 현재 실행 중인 인스턴스를 덮어써도 되는지
- 백업 시각이 원하는 상태 이후인지 이전인지

### 백업 절차

권장 순서는 아래와 같다.

1. 지금 상태를 바꾸는 작업을 잠시 멈춘다.
2. 가능하면 진행 중인 heartbeat나 대규모 상태 변경이 끝난 뒤 백업한다.
3. 데이터베이스 백업을 먼저 만든다.

```sh
pnpm paperclipai db:backup
# 또는
pnpm db:backup
```

4. 백업 파일이 현재 활성 인스턴스의 `data/backups` 아래 생겼는지 확인한다.
5. 코드 상태는 아래 둘 중 하나 이상으로 남긴다.

- git 커밋 + 포크 push
- 소스 zip 백업

6. 회사 상태까지 통째로 보존하려면 인스턴스 디렉터리 백업도 함께 만든다.

권장 보존 대상:

- 코드 저장소
- 현재 활성 인스턴스의 `db`
- 필요하면 현재 활성 인스턴스 전체

### 복구 판단 절차

복구는 아래 셋 중 무엇이 필요한지 먼저 구분한다.

1. 코드만 복구
2. 회사 데이터만 복구
3. 코드와 회사 데이터를 함께 복구

판단 기준:

- UI 문자열, 로컬 패치, 실행 스크립트 문제면 보통 코드 복구
- 이슈, 에이전트, 승인 상태가 꼬였으면 보통 회사 데이터 복구
- 둘 다 어긋났으면 전체 복구

### 코드 복구 절차

1. 현재 브랜치와 변경 사항을 확인한다.
2. 되돌릴 기준 커밋이나 포크 브랜치를 정한다.
3. git 또는 소스 zip으로 코드만 복구한다.
4. Paperclip을 다시 실행해 UI/런처가 원하는 상태인지 확인한다.

### 회사 데이터 복구 절차

1. Paperclip 프로세스를 중지한다.
   기본 dev runner를 쓰는 경우 먼저 `pnpm dev:list`로 현재 프로세스를 확인하고, 가능하면 `pnpm dev:stop`으로 정리한다.
2. 현재 활성 인스턴스 디렉터리를 다른 이름으로 한 번 더 백업한다.
3. 복구 기준 백업에서 `db` 또는 전체 인스턴스 디렉터리를 꺼낸다.
4. 현재 활성 인스턴스 경로에 덮어쓴다.
5. Paperclip을 다시 시작한다.
6. 아래를 확인한다.

- 회사 목록
- 에이전트 목록
- 핵심 이슈 상태
- 승인 상태

### 전체 복구 절차

1. 코드 복구 절차를 먼저 수행한다.
2. 그 다음 회사 데이터 복구 절차를 수행한다.
3. 실행 후 아래를 함께 검증한다.

- UI가 기대한 버전인지
- 회사와 이슈 상태가 기대한 시점인지
- 런처가 정상 동작하는지

### 복구 후 최소 검증 체크

복구 직후 최소 아래를 확인한다.

1. 현재 인스턴스가 사용하는 앱 주소에 접속 가능
2. 올바른 회사가 보임
3. CEO / CTO / CMO 등 핵심 에이전트 상태 확인
4. 핵심 이슈가 예상 상태인지 확인
5. 최근 승인 내역이 예상과 맞는지 확인

기본 환경이라면 앱 주소는 보통 `http://127.0.0.1:3100`이지만, worktree 또는 커스텀 인스턴스는 포트가 다를 수 있다.

## 19. 마지막 체크

운영자는 최종 승인 전에 아래 질문에 모두 `예`라고 답할 수 있어야 한다.

- 지금 이 결과물이 처음 목표와 이어지는가
- 누가 왜 판단했는지 Paperclip 안에 기록이 남아 있는가
- 다음 담당자가 바로 이어받을 수 있는가
- 필요하면 오늘 상태를 백업하고 되돌릴 수 있는가

하나라도 `아니오`면, 승인 대신 `in_review`, `blocked`, `revision_requested`, `rejected` 중 더 맞는 상태를 선택한다.
