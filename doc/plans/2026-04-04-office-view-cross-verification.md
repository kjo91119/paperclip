# 2026-04-04 2D 오피스 뷰 교차검증 지시서

## 1. 목적

이번 변경은 기존 Paperclip 보드를 대체하지 않고, 회사 상태를 가볍게 시각화하는 `2D 오피스` 화면을 추가하는 작업이다.

검증 목표:

- 새 오피스 라우트가 정상 진입되는지 확인
- 오피스 화면이 기존 회사 데이터와 연결되는지 확인
- 에이전트/이슈/라이브 런 상태가 2D 공간에 일관되게 반영되는지 확인
- 기존 내비게이션과 앱 흐름을 깨지 않는지 확인
- 커밋/푸시 전 상태로 받아들여도 되는지 판단

## 2. 검증 범위

이번 교차검증 범위에 포함되는 파일:

- `ui/src/App.tsx`
- `ui/src/components/Sidebar.tsx`
- `ui/src/components/CommandPalette.tsx`
- `ui/src/index.css`
- `ui/src/pages/OfficeView.tsx`
- `ui/src/pages/officeViewModel.ts`
- `ui/src/pages/OfficeView.model.test.ts`

이번 교차검증 범위에 포함되지 않는 것:

- 로컬 전용 `.cmd` 실행기나 바탕화면 바로가기
- STUDIOJUN 실제 데이터 자체의 정확성
- 기존 `company-import-export-e2e` 플레키의 근본 원인 수정

주의:

- 로컬 실행기 변경은 현재 저장소 커밋 범위에 포함되지 않는다.
- 따라서 이번 검증은 저장소에 반영될 UI 변경만 기준으로 판단한다.

## 3. 변경 요약

이번 변경으로 추가된 사용자 흐름:

1. 회사별 보드 라우트 아래에 `/<companyPrefix>/office` 추가
2. 사이드바에 `오피스` 메뉴 추가
3. 커맨드 팔레트에 `Office` 페이지 진입 항목 추가
4. 에이전트 상태를 다음 구역으로 매핑하는 2D 장면 추가

- `command`: 실행 중 / 라이브 런
- `desks`: 일반 작업
- `review`: 검토 중 작업
- `approval`: 승인 대기
- `recovery`: 일시중지 / 오류 / 종료 상태
- `lounge`: 아직 활성 작업이 없는 대기 상태

## 4. 사전 준비

저장소 루트에서 아래를 준비한다.

```sh
pnpm install
pnpm dev
```

기본 진입 URL:

```text
http://127.0.0.1:3100/STU/office
```

STU 회사가 존재하지 않으면, 현재 로컬 환경에서 실제 회사 프리픽스를 사용한다.

## 5. 자동 검증 결과

작성자 기준 현재 결과:

- `pnpm -r typecheck`: 통과
- `pnpm exec vitest run ui/src/pages/OfficeView.model.test.ts`: 통과
- `pnpm build`: 통과
- `git diff --check`: 통과

전체 테스트 참고:

- `pnpm test:run`은 이번 변경과 무관한 기존 플레키 1건으로만 실패
- 실패 위치: `cli/src/__tests__/company-import-export-e2e.test.ts`
- 실패 유형: packaged CLI E2E 서버 헬스체크 타임아웃

교차검증 중 이 플레키만 동일하게 보이면, 새 오피스 변경 자체의 회귀로 바로 단정하지 않는다.

## 6. 수동 교차검증 절차

### A. 라우트 진입

1. `/<companyPrefix>/office`로 직접 진입한다.
2. 빈 화면, 404, 무한 로딩이 아닌지 확인한다.
3. 상단 제목이 `회사명 오피스` 형태로 보이는지 확인한다.

기대 결과:

- 오피스 페이지가 열려야 한다.
- 회사가 선택된 상태라면 별도 설정 없이 바로 렌더링되어야 한다.

### B. 사이드바 진입

1. 왼쪽 메뉴에 `오피스` 항목이 추가되었는지 본다.
2. `대시보드 -> 오피스 -> 받은 편지함` 이동이 정상인지 확인한다.
3. 오피스 메뉴 선택 시 활성 상태가 표시되는지 본다.

기대 결과:

- 사이드바에서 새 페이지로 진입 가능해야 한다.
- 기존 메뉴 강조/선택 상태를 깨지 않아야 한다.

### C. 커맨드 팔레트 진입

1. `Cmd+K` 또는 `Ctrl+K`를 연다.
2. `Office` 항목이 Pages 그룹에 보이는지 확인한다.
3. 해당 항목 선택 시 오피스 페이지로 이동하는지 본다.

기대 결과:

- 키보드 기반 진입도 동작해야 한다.

### D. 장면 구성 확인

1. 중앙 장면에 아래 구역이 보이는지 확인한다.

- Command Screen
- 복구 구역
- 집중 데스크
- 검토 테이블
- 승인 게이트
- 라운지

2. 장면이 단색 박스가 아니라 배경, 데스크, 상태 카드가 있는 하나의 공간처럼 읽히는지 본다.
3. 에이전트 마커가 화면 밖으로 튀지 않는지 확인한다.

기대 결과:

- 2D 장면 구조가 한눈에 읽혀야 한다.
- 마커가 겹치더라도 완전히 보이지 않거나 클릭 불가능한 수준이면 안 된다.

### E. 상태 매핑 확인

가능하면 실제 STU 데이터 상태를 기준으로 아래를 확인한다.

1. 라이브 런이 있는 에이전트는 지휘 보드 근처를 순환하는지 본다.
2. `pending_approval` 에이전트가 있으면 승인 게이트 쪽에 보이는지 본다.
3. `paused` 또는 `error` 에이전트가 있으면 복구 구역 쪽에 보이는지 본다.
4. `in_review` 작업을 맡은 에이전트가 검토 테이블 쪽으로 가는지 본다.
5. 활성 작업이 없는 에이전트는 라운지 또는 일반 데스크에 배치되는지 본다.

기대 결과:

- 상태 변화가 전혀 무관한 위치에 보이면 안 된다.
- 라이브 런은 가장 눈에 띄는 영역에 보여야 한다.

### F. 상호작용 확인

1. 에이전트 마커를 클릭한다.
2. 해당 에이전트 상세 페이지로 이동하는지 확인한다.
3. 장면 내 이슈 카드가 있으면 클릭한다.
4. 해당 이슈 상세 페이지로 이동하는지 확인한다.

기대 결과:

- 오피스 뷰가 기존 상세 화면으로 이어지는 “요약 입구” 역할을 해야 한다.

### G. 우측 요약 패널 확인

1. `라이브 런` 카드에 현재 실행 중인 에이전트가 보이는지 확인한다.
2. `작업 큐` 카드에 열린 작업이 보이는지 확인한다.
3. `최근 활동` 카드에 최근 activity 이벤트가 보이는지 확인한다.

기대 결과:

- 메인 장면만 예쁘고 정보 패널이 비어 있으면 안 된다.
- 우측 패널 내용은 현재 회사 상태와 대체로 일치해야 한다.

### H. 반응형 확인

1. 데스크톱 폭에서 레이아웃이 무너지지 않는지 본다.
2. 모바일 폭에서도 최소한 스크롤 가능한 형태로 읽히는지 확인한다.
3. 텍스트 겹침, 버튼 잘림, 오버플로우가 심한지 본다.

기대 결과:

- 모바일에서 완전히 동일한 경험일 필요는 없지만, 사용 불가능하면 안 된다.

## 7. 반려 기준

아래 중 하나라도 확인되면 커밋 전 수정이 우선이다.

- `/office` 라우트가 열리지 않음
- 사이드바 또는 커맨드 팔레트 진입이 안 됨
- 에이전트나 이슈 클릭이 상세 화면으로 연결되지 않음
- 상태 매핑이 명백히 잘못되어 라이브 런과 복구/승인 상태가 구분되지 않음
- 장면이 모바일 또는 데스크톱 한쪽에서 심하게 깨짐
- 기존 대시보드/받은 편지함/이슈 화면 이동 흐름에 회귀가 생김

## 8. 승인 가능 기준

아래가 모두 맞으면 커밋 후 푸시 단계로 넘어가도 된다.

- 새 오피스 화면이 정상 진입된다
- 내비게이션 연결이 자연스럽다
- 상태 표현이 대체로 기대와 맞는다
- 자동 검증 결과에 새로운 실패가 없다
- 남아 있는 테스트 실패가 기존 알려진 `company-import-export-e2e` 플레키뿐이다
